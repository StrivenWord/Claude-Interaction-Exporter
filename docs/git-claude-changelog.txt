    Make the scheduled-runs filter actually filter the task table
    
    The checkbox only ever affected the bulk export, so on the browse page it
    looked inert. It now filters the table too, and there is a Scheduled column
    showing what is known about each session.
    
    The reason it wasn't already doing this: the session list doesn't say
    whether a schedule fired a run. That fact lives on the session's first
    event, so it has to be read per session. Rather than replay whole logs,
    this reads a single page — the first event is always on it — and remembers
    the answer, so toggling the filter afterwards costs nothing.
    
    Checking the box therefore does visible work the first time: sessions are
    checked a few at a time with progress in the section header, and rows drop
    out as answers arrive. Sessions whose origin isn't known yet stay visible
    rather than being hidden on a guess, and show a dash in the new column.
    
    The box now starts unchecked. Checked-by-default meant a fresh page had
    nothing resolved and nothing filtered, which is precisely why it read as
    doing nothing.
    
    Bulk export starts from what the table shows, so sessions already known not
    to be scheduled are no longer fetched just to be thrown away. The check
    after fetching stays, since it is the authoritative one and still covers
    sessions that were never resolved.
    
    Also logs one raw row of the list response. Its field names are undocumented
    and normalizeCoworkList is guessing at several of them, so a wrong guess
    should be visible rather than showing up as a blank column.

commit c062dff6ceb1dda71fe35b5fabb5163dcb275a90
Author: Paul Lee <paul@strivenword.com>

    Add export for scheduled tasks and other Cowork sessions
    
    Tasks run as Cowork sessions rather than chat conversations, so the
    exporter couldn't see them at all. They live behind a different endpoint
    and arrive as a flat event log instead of a message tree, which needed its
    own read and render path.
    
    Reading one session took some care:
    
    - The log is paged. A request returns roughly 160KB and stops, which for a
      task that ran tools is well short of the whole log, so the reader replays
      forward until a page adds nothing new.
    - The stream has no end. It replays the backlog and then stays open waiting
      for live events, so waiting for the body to finish never returns. It is
      now read incrementally and left once no event has arrived for a moment.
      Keepalive frames deliberately don't count as activity, or an idle stream
      would hold the read open forever.
    - Listing sessions refuses the request without an API version header. The
      endpoint says so in its response, which is now shown rather than reduced
      to a bare status code.
    
    Exported tasks keep the same shape as exported conversations, with
    frontmatter recording the routine that fired the run, its trigger, the
    model, and whether it was scheduled or started by hand. Tool activity —
    searches run, files written — is included when Metadata is checked, since
    for a research task that is the provenance, and a file the task wrote is
    often the real output.
    
    Three pieces of existing duplication got in the way and are now gone:
    
    - The default model timeline existed in two copies that had drifted apart.
      One of them carried a February 29th, which doesn't exist in 2025 and had
      been quietly rolling over to March 1st. Defined once now, with the dates
      the models actually shipped on.
    - The bulk export flow was 165 lines that tasks would have had to copy. It
      now takes a per-item renderer, so conversations and tasks share the
      progress display, the zip, the cancel button and the summary file.
    - The export settings were being read from the page in three places.
    
    Conversation exports are unchanged, verified byte for byte against the
    previous implementations across a set of fixtures.

commit ba0a3823a91a0f1cca9fd4d9fa6043ce62dea11b
Author: Paul Lee <paul@strivenword.com>
Date:   Fri Aug 21 08:53:11 2026 -0400

    Stop re-injection from leaving stale content script code live
    
    The manifest declares utils.js and content.js as content scripts, and
    background.js injects the same two files again for tabs that were already
    open. Both files declared top-level constants, and a duplicate top-level
    const is a parse-time error — so the second injection aborted the whole
    file and the earlier copy kept handling messages.
    
    After reloading the extension in developer mode this left a tab running new
    utils.js next to old content.js: the frontmatter emitted the new "tags: []"
    placeholder while the old message handler was still dropping the tags the
    popup sent, so a filled-in tags field produced an empty list no matter what
    was typed. The same hazard silently reverted any other content.js edit.
    
    Both files now avoid top-level const/let, and the message listener registers
    once per page, dispatching through the function binding so a re-injection's
    fresh code is what actually runs.

    Make per-export tags actually reach the exported files
    
    The tags field was wired into the popup but the content script never read
    it, so every export from the toolbar button wrote an empty tags value. Pass
    it through, and give tags a real shape everywhere they land:
    
    - Markdown frontmatter emits a YAML block sequence, the format Obsidian
      writes itself, instead of interpolating the raw string. The old version
      produced a single string rather than a list, and a "#"-prefixed entry
      turned into a YAML comment that silently parsed as nothing.
    - JSON exports carry a tags array on each conversation object.
    - Plain text exports get a Tags line in the metadata header.
    - Batch exports record the tags in export_summary.json.
    
    Input is cleaned rather than rejected: a leading "#" comes off, spaces
    inside a tag become hyphens, characters Obsidian won't accept in a tag are
    dropped, case is normalized, and duplicates collapse. Tags that a YAML
    parser would otherwise read as a number, date or boolean get quoted.
    
    Tags describe the export at hand, so the browse page no longer writes
    edits back over the saved default the way it does for project and
    contributor. The options page setting is now just a starting value.
    
    Also refreshes the README frontmatter example, which still listed the
    placeholder categories removed in 786151d.

    Add Claude Conversation Exporter Chrome extension
    
    Features:
    - Export individual conversations or bulk export all conversations
    - Multiple formats: JSON (with full data), Markdown, Plain Text
    - Browse page with search, filter by model, and sort capabilities
    - Automatic model inference for conversations with null models (default model)
    - Branch-aware exports (only exports current conversation branch)
    - ZIP archive creation for bulk exports with progress tracking
    - Organization ID configuration via options page
    
    Key capabilities:
    - Preserves complete model information (unlike official Claude.ai export)
    - Infers historical models based on conversation date
    - Plain text format uses Human:/Assistant: prefixes (abbreviated to H:/A:)
    - Handles conversation branches correctly
    - Beautiful UI with gradient-themed icons and header graphics
    
    Technical implementation:
    - Manifest V3 Chrome extension
    - Content script injection for Claude.ai pages
    - Background service worker for tab management
    - JSZip integration for creating ZIP archives
    - Shared utilities for code reuse
    
    Created by Claude Opus 4.1 in collaboration with human developer
